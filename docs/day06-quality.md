# День 6 — качество retrieval и защита от галлюцинаций

## Результат

Реальный прогон 5 октября 2026: шесть полных ответов, два частичных ответа и четыре честных отказа. При ручном чтении ответов не обнаружено неподтверждённых фактов из списка недопустимых утверждений. Три отказа произошли до LLM; вопрос о версии Weaviate потребовал проверки моделью. Это результат небольшого учебного набора, а не гарантия отсутствия галлюцинаций.

Выбрано: **chunk size 800 символов, overlap 160, semantic, top-k 5, cosine distance ≤ 0.16**. На подборе найдены 5/5 размеченных фактов, на проверочной половине — 7/7. Все восемь вопросов с подтверждаемой частью сохранили необходимые факты.

Рабочая коллекция не переиндексировалась. По умолчанию приложение по-прежнему использует 500/100 и top-k 3; новый порог 0.16 включён для обоих режимов. Рекомендованная конфигурация применяется явно.

## Методика и воспроизводимость

- Embedding: `intfloat/multilingual-e5-small`, revision `614241f622f53c4eeff9890bdc4f31cfecc418b3`; Weaviate `1.39.7`; LLM `deepseek-flash`.
- Исходные документы — только knowledge_base. Хеши документов и системной инструкции, тексты всех найденных чанков, UUID, метрики и полные ответы находятся в [JSON-отчёте](day06-quality.json).
- [12 вопросов](../tests/data/quality_questions.json): шесть отвечаемых, четыре отрицательных и два частичных. В обеих заранее выделенных половинах: три отвечаемых, два отрицательных и один частичный. Ожидаемые факты подтверждаются документами, а не конфигурацией проекта.
- 18 комбинаций: 300/60, 500/100, 800/160 × top-k 1, 3, 5 × semantic/hybrid (alpha=0.5). На каждой выполнено 12 поисков: 216 retrieval-запросов. Пороги 0.10–0.40 с шагом 0.01 и отсутствие фильтра оцениваются на сохранённой выдаче: 576 вариантов.
- Выбор использует только tune: сначала число найденных фактов, затем отказ на постороннем вопросе, меньше чанков без размеченного факта, меньше символов контекста, предпочтение прежней конфигурации при равенстве, меньший порог. Половина validation не участвует в выборе.
- Проверка факта требует и правильного source_name, и текстового маркера в одном чанке. Чанки без маркера считаются proxy-шумом; это не precision и не полноценная человеческая разметка релевантности.
- Hybrid score сохраняется для ранжирования. Для порога cosine distance вычисляется по сохранённому вектору чанка и вектору вопроса. Относительно нормализованный fusion score не является оценкой уверенности. См. [документацию Weaviate](https://docs.weaviate.io/weaviate/concepts/search/hybrid-search).

В выбранном режиме фильтр уменьшил 60 исходных чанков до 18, а суммарный текст контекста — с 41 660 до 12 483 символов.

Для обычных вопросов top-k 1 часто достаточно; для междокументного вопроса нужен чанк на четвёртой позиции. Поэтому top-k 5 компенсирует пропуск, а порог сокращает лишний контекст.

Важное ограничение chunking: все семь документов короче 800 символов после очистки. В этой конфигурации каждый документ становится одним чанком и overlap фактически не используется. Нельзя заключить, что 160 символов перекрытия оптимальны для длинных документов; эксперимент показывает пользу сохранения цельного короткого документа. При 300/60 появляются дополнительные фрагменты и повторяющиеся темы; при 500/100 причина или объяснение могут остаться в соседнем чанке.

## Проверки и ограничения

- Проверки: 128 unit-тестов, 4 integration-теста и 4 E2E-теста; Ruff, проверка форматирования, strict mypy и git diff --check. E2E Дня 6 и обновлённое сравнение Дня 5 выполнены с реальным LLM API.
- Проверены отказ без LLM после фильтра, граничное значение порога, неправильные метрики и векторы, сохранение порядка и перенумерация источников. Integration сравнивает hybrid distance с независимым расчётом по реальным векторам.
- Новый E2E проверяет 12 случаев и отдельную проверочную половину; полный отказ не содержит источников, частичные ответы используют подтверждённые источники. Grounded содержание и отсутствие запрещённых утверждений дополнительно проверены чтением ответов выше.
- В предварительных прогонах модель иногда помечала ответ о совместимой embedding-модели как частичный, в том числе при 800/160. В инструкции уточнено: достаточный ответ может прямо следовать из текста, необязательные технические подробности не нужны. Запрет внешних сведений сохранён. Даже после этого в одном из прогонов старого теста ответ был частичным: база содержит требование совместимости, но не детальный механизм несопоставимости векторов разных моделей. В тестовом наборе Дня 5 вопрос уточнён до прямо записанного факта: что обычно нужно сделать с векторами индекса при замене embedding-модели. Формулировка не запрашивает подробный механизм совместимости или названия моделей, отсутствующие в документах. Строгое требование полного ответа сохранено; набор Дня 6 и параметры retrieval после проверки не менялись.
- Порог не решает вопрос отсутствующего факта в близком документе: версия Weaviate проходит retrieval-фильтр, но отсутствует в контексте. Отказ LLM и проверка ссылок остаются необходимыми; ссылки сами по себе не доказывают истинность текста.
- Порог 0.16 подобран совместно с конфигурацией 800/160; при прежних defaults и при изменении корпуса его полнота может отличаться. Для другой модели или базы нужна новая калибровка. Небольшая выборка не оценивает частоту ошибок или стабильность LLM. Validation не используется для подбора retrieval-параметров, но часть формулировок уже существовала в тестах Дня 5; это не полностью независимый статистический holdout.

## Повторный запуск

```shell
uv run rag-evaluate --report /tmp/day06-retrieval.json
uv run rag-evaluate --report /tmp/day06-quality.json --generate
DAY06_REPORT_PATH=/tmp/day06-quality.json \
  uv run pytest -m e2e tests/e2e/test_quality_pipeline.py
uv run pytest tests/unit
uv run pytest -m integration tests/integration
uv run pytest -m e2e tests/e2e
uv run ruff check .
uv run ruff format --check .
uv run mypy
```

Эксперимент создаёт коллекцию с уникальным именем и удаляет только её в finally. Рабочая коллекция не изменяется. Отчёт сохраняется до проверки ответов и после каждого ответа; при ошибке остаются уже собранные данные. Запуск с генерацией использует настроенный реальный LLM API.
