## 2. Почему документы и вопрос нужно кодировать одной embedding-моделью?

**Чанк 1:**

> Благодаря этому semantic search способен находить контекст не только по точному совпадению терминов.
> Документы и пользовательский вопрос должны кодироваться совместимой embedding-моделью. Замена модели обычно требует пересоздания всех векторов в индексе. Размерность вектора также должна совпадать с настройками хранилища.
> Секреты доступа к embedding API не сохраняют в коде или репозитории. Их передают через переменные окружения, а ошибки сети и ограничения API обрабатывают явно.

**Чанк 2:**

> также способ векторизации. Если embeddings вычисляет приложение, в Weaviate передают готовый вектор. Такой режим позволяет контролировать модель и повторно использовать один и тот же embedding-клиент.
> Перед массовой загрузкой полезно создать коллекцию и проверить соединение. Повторная индексация должна учитывать дубликаты, иначе одинаковые чанки ухудшат результаты поиска.

**Чанк 3:**

> Semantic retrieval
> Retrieval получает вопрос пользователя, строит его embedding и запрашивает у Weaviate несколько ближайших чанков. Параметр top-k ограничивает число результатов. Малое значение может пропустить полезный контекст, а слишком большое добавляет шум и расходует контекстное окно модели.
> Одной сортировки по близости недостаточно. Результаты полезно отфильтровать по порогу релевантности и сохранить исходный score.

> Retrieval получает вопрос пользователя, строит его embedding и запрашивает у Weaviate несколько ближайших чанков. Параметр top-k ограничивает число результатов. Малое значение может пропустить полезный контекст, а слишком большое добавляет шум и расходует контекстное окно модели.
> Одной сортировки по близости недостаточно. Результаты полезно отфильтровать по порогу релевантности и сохранить исходный score.

## Оценка после просмотра выдачи

Просмотрены все 30 фрагментов: пять вопросов, два режима, три результата.
Во всех десяти поисках первый чанк содержит ожидаемый факт: hit@1 и hit@3 — 5/5
для каждого режима на этом наборе. Первые результаты объясняют сохранение
информации на границах чанков, совместимость embeddings, метаданные в Weaviate,
компромисс top-k и оценку поиска отдельно от генерации ответа.

Дополнительные результаты менее точны. Например, для вопроса о перекрытии
оба режима поставили общие рекомендации о retrieval на второе место: этот чанк
не объясняет перекрытие. Для вопроса о метаданных hybrid поднял на вторую позицию
`02_chunking.txt` (chunk_id=1), где прямо перечислены имя файла и номер чанка;
semantic вместо этого вернул описание supplied vectors и процесса retrieval.
Для вопроса о совместимой модели hybrid поменял местами второй и третий чанки.

Hybrid не улучшил top-1 на этих пяти вопросах: semantic уже нашёл нужные факты
первым результатом. Эти результаты подтверждают работоспособность учебного
набора, но не доказывают превосходство одного режима на других данных. Без
порога релевантности top-k может включать шум; уверенного отказа для вопросов,
ответа на которые нет в базе, этот этап пока не обеспечивает.

## Воспроизведение

```shell
docker compose up -d
uv run rag-kb
uv run rag-query "Зачем соседние чанки частично перекрываются?" --top-k 3
uv run rag-query "Зачем соседние чанки частично перекрываются?" --top-k 3 --mode hybrid --alpha 0.5
uv run pytest -m e2e tests/e2e/test_retrieval_pipeline.py
```

Автоматическая проверка требует ожидаемый источник и факт в top-3 каждого
режима. Точные distance/score в тесте не фиксируются. При проверке прошли 53
unit-теста, 3 integration-теста и 2 e2e-теста; Ruff и mypy также прошли.
